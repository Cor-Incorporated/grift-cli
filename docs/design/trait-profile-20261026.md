## 0. 要点

grift の目的は、MBTI 診断のように順位はつけずに、その人の進め方に合わせて案件と照らせるようにすることです。0.8.0 の出力は数字と分母を正しく出していますが、読む人が「この人はこういう進め方をする」と言葉にできる形になっていません。

- 0.8.0 の実出力 8 本を 3 者の目で読み、詰まる所を 33 か所挙げました（§1.3）。多いのは、英語の内部名、意味の説明がない数字、良し悪しや順位に見える語です。読む途中で見つけた 0.8.0 の食い違い 9 件と、別のセッションが見つけた docs の食い違い 1 件を §1.4 に記録しました。
- MBTI から借りるのは「読んで自分のことだと分かる言葉で書く」「相性を考える材料になる」ところだけです（§2）。タイプ名も群も付けません。グルーピング調査で、群は人の進め方ではなく「どの repo の人か」の言い換えだったためです（§8 の 1）。
- 3 案を比べ、案 C を勧めます（§3）。軸ごとに平易な文と件数を出し、エンジニア側の希望も受けて、案件側とエンジニア側の両方から照らします。0.9.0 に入れるのは段階 1（文章、面談の問い、強弱語を外すこと、§1.4 の修正）までにし、エンジニア側の希望（actor brief）は段階 2 に分けます。
- 見本は §4 と `samples/` にあります。数字はすべて 0.8.0 が合成リポジトリで実際に出した値です。
- 判断してほしいことは §8 の 5 点で、2026-10-26 に結論が出ました。段階 1 を 0.9.0 で進め、ラベルは付けません（§8）。

| 順位になるか | タイプに優劣は無いと説明される | 点数も順位も無い。人の一覧は id 順（0.8.0）。ただし強弱語と量の数字は比べたくなる（§1.3 # 9、# 16） | 比べる相手を、本人のほかの仕事に限る。量で文を選ばない |
| 本人が納得できるか | 「当たっている」と感じやすい文で書かれる | 内部名と小数が多く、自分のことと感じにくい | 本人の仕事の言葉で書き、本人のひとことを添えられる |
| 案件と照らせるか | 倫理規定が、採用の選別や雇用の判断に使うことを認めていない | `grift align` で案件の宣言と軸ごとに並べ、5 通りで出す。面談で聞くことは出ない | 両側から「重なっている点」と「面談で確かめたい点」を出す |
| 変わるものとして扱うか | 本人の好みとして説明される。再検査で別のタイプになる人が少なくないという批判がある | 窓（180 日）と定義版で値が変わると書いてあるが、目立たない | 期間を冒頭に書き、「この期間の記録」として読ませる |
| 確からしく見せる仕掛け | 4 文字の型と心理学の語 | 内部名と小数 4 桁が精密そうに見える | 小数を減らし、件数（分子と分母）で書く |

出典と確かめた範囲は次のとおりです。

- The Myers & Briggs Foundation が公開している MBTI の倫理規定は、結果を人のラベル付け・評価・制限に使わないこと、採用の選別や雇用の判断に使わないこと、タイプは能力を表さないことを定めています（「MBTI Code of Ethics」、<https://www.myersbriggs.org/using-type-as-a-professional/mbti-code-of-ethics/>、2026-10-26 に確認）。
- 再検査の安定性への批判は Pittenger, D. J. (2005). Cautionary comments regarding the Myers-Briggs Type Indicator. Consulting Psychology Journal: Practice and Research, 57(3), 210-221 によります。原典は読んでいません。二次資料で、数週間後の再検査で別のタイプになる人が少なくないと紹介されていることだけを確かめました（未検証）。
- 「自己申告の質問紙、4 つの軸、16 タイプ」という仕組みは一般的な説明によります。出版元の資料では確かめていません（未検証）。
- 型ラベルを出す近い道具に、EIS（Engineering Impact Signal）があります。7 つの軸を固定の比重で 0〜100 にまとめ、型ラベルとチームの横並びを出す道具で、TEP はそれと分ける立場を取ってきました（[読み方ガイド](../metrics-guide.md)の「関連する指標・ツール」）。

MBTI の倫理規定自身が「ラベル付けに使わない」「選別に使わない」と書いていることは、この設計の前提と同じ向きです。似せるのは読みやすさで、型そのものではありません。

### 2.2 似せるべき点と、似せてはいけない点

似せるべき点は 4 つです。

1. 読んで自分のことだと分かる。内部名ではなく仕事の言葉で書きます（「サーバー側の処理」「画面から通しで動かすテスト」）。
2. 言葉で説明される。軸ごとに先頭の 1 文で進め方を書き、数字はその後ろに根拠として置きます。
3. 相性を考える材料になる。案件の要望と並べたとき、重なっている所と確かめたい所が言葉で出ます。
4. 本人の言葉を添えられる。MBTI の自己申告のよい所は、本人が自分を語れることです。grift では観測と混ぜず、申告と分かる欄に置きます。

似せてはいけない点も 4 つです。

1. タイプに押し込める。16 タイプのような 1 語のまとめを作りません。軸ごとの文を 1 つの名前に畳むと、分母が消えます（ギャップ表 行 10、架空の物語「スコアにした途端、条件が見えなくなる」と同じ理由です）。
2. 科学的に見せかける。「性格」「資質」「適性」の語を使いません。ファイルの置き場所の決まりで数えていることを、文のそばに書きます。
3. 変わらない性格のように扱う。期間と定義版を必ず書き、「この期間の記録」として読ませます。
4. 二択に分ける。境目の近くの人を反対側に振り分けません。境目を使う所でも、数字を同じ段落に出します。

## 3. 設計案

### 3.1 3 案に共通する前提

どの案も次の 7 つを守ります。ADR-0002 では T1〜T7 として書きます。

1. 量ではなく自分の仕事の割合と形を言葉にします。文を選ぶのに、件数・日数・行数の大きさは使いません。使うのは「自分の変更のうち何件か」と、間隔の形（真ん中の値と、10 回に 9 回が収まる値）だけです。
2. 比べる相手は本人のほかの仕事だけです。「多い」は「その人の変更の中で多い」という意味で使い、ほかの人や参照分布と比べた語（上位、平均より）は使いません（ADR-0001 R3）。
3. 数字を消しません。文ごとに、分子・分母・期間を同じ段落か根拠の表に置きます。
4. 合計しません。照らし合わせで「重なった項目の数」や「N 項目中 M 項目」を出しません。数えると合成点になります。
5. 文と問いは、公開した決定表で数字から機械的に選びます。LLM は使いません。決定表は、定義版を上げるときに一緒に改めます。
6. 本人向けの文は、本人申告と同意の記録があるときだけ出します。`attribution_state = "claimed"` かつ `consent = "recorded-explicit-consent"` のときです。公開リポジトリの第三者（`inferred_actor`）と、管理者が登録した identity（`verified`）には出しません。norms は本人向けの表示を claimed にだけ許しています（§4）。
7. 文に良し悪しの語を入れません。既存の語彙の検査（`check_forbidden_vocab.py`、`tests/test_gloss_gates.py` の NORMATIVE、`tests/test_v070_complementarity.py` の順序の語）を、すべての定型文に当てます。

### 3.2 案 A: 特性プロフィール（ラベルなし）

本人のレポート（report-v2 の actor）の Markdown の先頭に、「この記録から見える進め方」という節を置きます。4 つの観点ごとに先頭の 1 文と根拠の数字を出し、続けて「この記録では見えないこと」「面談で確かめたいこと」「数字の読み方と限界」「根拠」の表を並べます。0.8.0 の詳しい数字の節は、この節の後ろに残ります。案件のレポート（`grift project`）でも、案件のリポジトリについて同じ形の文を出します。照らし合わせ（`grift align`）の Markdown は「要望と記録が重なっている点」「面談で確かめたい点」「案件側が書いていないこと」の 3 つに組み直します。

JSON は変えません。文は Markdown にだけ出し、文の選び方は下の決定表で、JSON の数字から誰でも作り直せるようにします。JSON に文やその id を入れると、機械で絞り込める型ラベルと同じ働きをするためです。

#### 文の決定表

| 観点 | 使う数字（report-v2） | 文を出さない条件 | 先頭の文 | 続く文 |
|---|---|---|---|---|
| どこを触るか | `surface_profile.surface_commit_counts`（分母は path が取れた自分の non-merge commit） | 分母が 20 未満 | 「いちばん多いのは{場所}で、自分の変更 {n} 件のうち {c} 件です。」。同じ件数の場所は SURFACES の順で並べて書きます。test は「どう確かめるか」で扱うので除きます | 「次いで、{場所}（{c} 件）…にも触れています。」。0 件より多い場所を件数の多い順に 4 つまで |
| どんな間隔で出すか | `change_rhythm.median_gap_days`、`p90_gap_days`、`burst_share_le_2d`、`long_gap_share_ge_30d`、`interval_sample_size` | 間隔が 20 回未満 | 30 日以上の間隔が 0 回で、10 回に 9 回が 7 日以内なら「間をあまり空けずに出す進め方です。」。30 日以上の間隔が 1 回以上あり、2 日以内の間隔が半分以上なら「続けて出す時期と、長く空く時期がある進め方です。」。どちらでもなければ先頭の文は出しません | 「変更と変更の間隔は、真ん中の値が {m} 日で、10 回に 9 回は {p} 日以内でした。」。{m} は小数 1 桁に丸め、{p} は小数 1 桁に切り上げます（「以内」を保つため）。続けて 2 日以内と 30 日以上の回数 |
| どう確かめるか | `verification_profile.test_touch_share` の分子（surface の test の件数）、`test_type_distribution`、`fix_with_test_pairing` | 検証の観測が not_observed。理由を平易な文で出し、「テストを書いていないという意味ではありません」を添えます | 「テストのファイルも一緒に変えた変更が、{n} 件のうち {c} 件あります。」 | 0 件より多い種類を件数つきで。直しの変更が 20 件以上なら「直し（fix）の変更 {s} 件のうち {w} 件で、テストも一緒に変えています。」、20 件未満なら「直しの変更は {s} 件で、20 件に届かないため、テストとの組み合わせは数えていません。」 |
| 作るか、手を入れるか | `role_profile.dimensions.work_type.create` と `modify`、`process_position.integrator` と `release` | role_profile が not_observed（同意の記録が無いときを含む） | 手を入れる変更のほうが多ければ「すでにあるファイルに手を入れる変更（{m} 件）のほうが、新しいファイルを作る変更（{c} 件）より多い進め方です。」。作る変更のほうが多ければ逆。同じなら「新しく作る変更と、手を入れる変更が同じ数です。」 | 取り込み（merge）とリリースの印（タグ）が 1 件以上あれば回数 |

境目を使うのは「どんな間隔で出すか」の先頭の文だけです。7 日（1 週間）、半分、30 日（0.8.0 にある長い間隔の定義）という区切りを使いますが、根拠のある値ではなく読みやすさのための区切りです（未検証）。境目の近くでも、真ん中の値と 10 回に 9 回の値を同じ段落に出すので、数字は消えません。ほかの観点は、件数の大小の比べ（自分の変更の中で）だけで文を選びます。

### 3.3 案 B: 言葉の組み合わせ

軸ごとに閉じた語の集まりを決め、その組み合わせで人を短く表します。たとえば候補者 A は「サーバー側中心・間を空けずに・単体テストあり・手を入れる側（2025-11〜2026-10、変更 97 件）」になります。JSON にも、軸ごとの語を入れるキー（`trait_words`）を足す案です。

覚えやすく、営業が表計算に貼りやすい形です。MBTI の 4 文字に近い読みやすさがあります。

一方で、組み合わせはタイプ名と同じ働きをし、語だけが転記されると件数と期間が消えます。語の境目（たとえば「中心」は 4 割以上）の近くでは、少しの差で語が変わり、越えるための操作の得が大きくなります。表計算で語を絞り込むことは、境目による選別そのものです。ギャップ表 行 10 の判断、架空の物語「スコアにした途端、条件が見えなくなる」、MBTI の倫理規定（ラベル付けに使わない）と、どれも食い違います。

### 3.4 案 C: 両側から照らす

案 A の文と問いをそのまま使い、エンジニア側の希望（`tep-actor-brief-v1`、0.8.x 計画の在庫 #8）を受けて、照らし合わせを両方向にします。

1. 案件の要望 → この人の記録（0.8.0 にある向き。案 A の形に組み直す）
2. この人の希望 → 案件のリポジトリの記録（新しい向き。案件側が `grift project REPO` の結果を渡したときだけ）
3. 宣言どうし（共有できる記録と、案件が共有を求める記録のように、どちらも宣言の項目）

エンジニアが書くのは、案件に求めること（希望）です。できることの申告ではありません。書き方の案は `inputs/brief-a.toml` と `inputs/brief-b.toml` にあります。

| 群 | キー | 中身 | 案件のどの記録と並べるか |
|---|---|---|---|
| やりたい場所・避けたい場所 | `wishes.surfaces.prefer` / `avoid` | tep-project-v1 と同じ 11 の場所 | 案件のリポジトリの surface の件数 |
| あってほしい確かめ方 | `wishes.verification.prefer` | unit / integration / e2e / contract / unspecified | 案件のリポジトリのテストの種類 |
| 共有できる記録 | `sharing.inputs` | git / forge / tracker | 案件の `requirements.inputs`（宣言どうし） |
| 本人のひとこと | `note.text` | 200 字まで。grift は確かめず、申告としてそのまま載せる | 並べない |

進め方（間隔）の希望は最初の版では入れません。案件のリポジトリの間隔はチームの出し方で、1 人の働き方の条件と同じ物差しになるかが分からないためです（未検証。SES の営業とエンジニアに聞いてから決めたい）。

照らし方は案 A の決定表と同じ 5 通りの並びを使い、出し方だけを変えます。

| 希望 | 案件のリポジトリの記録 | 出し方 |
|---|---|---|
| やりたい場所、あってほしい確かめ方 | 1 件以上 | 表に件数を並べる |
| やりたい場所、あってほしい確かめ方 | 0 件 | 「希望の側から確かめたい点」に「{本人}は{場所}を希望しています。案件のリポジトリには{場所}の変更が 0 件です。この案件に{場所}の仕事があるか（別のリポジトリで管理していないか）を、案件側に確かめてください。」 |
| 避けたい場所 | 0 件 | 表に「0 件」と並べる |
| 避けたい場所 | 1 件以上 | 「{本人}は{場所}を避けたいと書いています。案件のリポジトリには{場所}の変更が {c} 件あります。この案件でどれくらい担当するかを、両方で確かめてください。」 |
| 共有できる記録 | 案件の要望と重なり、まだ渡されていない | 「宣言どうしで確かめたい点」に、記録を受け取る手順 |
| 共有できる記録 | 案件の要望と食い違う | 「宣言どうしで確かめたい点」に「出すかどうかを、本人と案件側で話してください。」 |
| どれでも | 案件のリポジトリの記録が無い | 「案件のリポジトリの記録が無いので、希望の側からは照らせません。案件側に `grift project REPO` の結果を頼んでください。」 |

本人のひとことは、MBTI で人が感じる「自分のことが書いてある」感じ（当事者性）を、観測を変えずに足す欄です。たとえば候補者 A のひとこと「画面の仕事は前の職場で 1 年ほどしました（非公開のリポジトリです）」は、画面の変更が 0 件であることの事情を、本人の言葉で残します。grift は確かめないので、見出しに「申告。grift は確かめていません」と必ず書きます。文には既存の語彙の検査と秘密の検査（`assert_no_secrets`）を当てます。

### 3.6 推奨: 案 C を 2 段階で入れる

案 C を勧めます。0.9.0 には段階 1（案 A と共通の部分）を入れ、actor brief は段階 2 に分けます。

1. ユーザーの目的は「案件側とエンジニア側の両方から判断できる」ことで、両方向を持てるのは案 C だけです（ギャップ表 行 9）。
2. 段階 1 は入力も schema も増やさずに「専門用語だらけ」「数字だけで意味が分からない」を直せます。JSON は変えず、Markdown の先頭に文と問いを置くだけです。
3. 案 B はタイプ名と同じ働きをし、ギャップ表 行 10、架空の物語、MBTI 自身の倫理規定と食い違います。覚えやすさは案 A の先頭の文でも得られます（§4.5）。
4. actor brief の項目（とくに進め方の希望）は、営業とエンジニアに聞いてから決めたい点が多く残っています。段階を分ければ、段階 1 を使ってもらいながら決められます。

### 3.7 軸の候補（量と形の区別）

グルーピングの調査（grift-match の [`docs/research/grouping-feasibility-2026-10.md`](https://github.com/Cor-Incorporated/grift-match/blob/cf0d148/docs/research/grouping-feasibility-2026-10.md)）が読むための一覧として書きました。調査は 2026-10-26 に判定 C「できない」を出し、ラベルは付けないと決めました（§8 の 1）。軸と、調査で確かめた範囲の対応は、報告の §5.6 にあります。群の作り方は調査の側で決めるので、ここでは軸と、使う数字が自分の仕事の中の割合や形なのか、量なのかだけを書きます。どれも 0.8.0 の report-v2 から取れる数字で、新しい観測は足していません。

| 軸 | 使う数字（report-v2） | 分母 | 形か量か | 同意の記録 | 膨らませ方 |
|---|---|---|---|---|---|
| どこを触るか | `surface_profile.surface_commit_share` の 11 の場所（文では test を除く 10） | path が取れた自分の non-merge commit（`surface_commit_share.population`） | 形（自分の変更の中の割合）。1 件の変更が 2 つ以上の場所に入るので、合計は 1 を超える | 要らない | その場所のファイルに小さな変更を足すと上がる |
| どんな間隔で出すか | `change_rhythm.median_gap_days`、`p90_gap_days`、`burst_share_le_2d`、`long_gap_share_ge_30d` | 180 日窓の中の間隔の数（`interval_sample_size`） | 形（間隔の散らばり） | 要らない | 小さく分けて毎日出すと短くなり、まとめて出すと長くなる |
| どう確かめるか | `verification_profile.test_touch_share`、`test_type_share`（unit / integration / e2e / contract / unspecified）、`fix_with_test_pairing` | `test_touch_share` は自分の non-merge commit。`test_type_share` はテストのファイルを触った commit。`fix_with_test_pairing` は fix・revert の件名の commit で、20 件以上のときだけ値が出る | 形 | 要らない | テストのファイルに 1 行足すと上がる |
| 作るか、手を入れるか | `role_profile.dimensions.work_type`（create / modify / rename / test / dependency / corrective）、`process_position`（creator / maintainer / integrator / release） | 自分の non-merge commit。`process_position` は工程の信号の合計 | 形 | 要る（claimed か verified に、同意の記録） | 新しいファイルを足す、取り込みを増やす、タグを打つと動く |

この設計は、量の代理になる数字を文の選び方に使いません（T1）。`change_rhythm.active_days_180d` と `window_population`、`surface_commit_counts` などの件数そのもの、`activity` の数字、`context_profile` の規模の数字（`scale`、`top_actor_share`、`resolved_human_actors`）がこれに当たります。群の入力に使うかどうかは調査の側の判断ですが、使えば量で人を分けることになり、ADR-0001 の R1・R2 に当たります。参照分布の位置（`interpretation.decile`）は、人の順位に読まれるので使いません（ADR-0001 R3）。

時期（`role_profile.dimensions.time`）は「この期間の記録」として読ませるための文脈で、軸には入れていません。案件のリポジトリ（project-v1 の observed）からは、「作るか、手を入れるか」を除く 3 つが同じキーで取れます。

## 8. 判断してほしいことと、その結論

2026-10-26 に、ユーザーが次のとおり決めました（親セッション経由）。段階 1 を 0.9.0 で進めます。判断 1 は同じ日にグルーピング調査の判定を受けて決めました。

| 2 | actor brief を入れるか。項目は 4 群でよいか | 推奨どおり。段階 2 で入れ、0.9.0 には入れない |

| 4 | 本人向けの文を出す相手を claimed に限るか | 推奨どおり。claimed と同意の記録があるときだけ出す。verified には出さず、出していない理由を書く |

提案したときの文は次のとおりです。

1. ラベル（タイプ名）を付けるか。推奨は付けないことです（案 B を採らない）。覚えやすさは軸ごとの先頭の文で補います。ラベル（群）を付けるかは、グルーピング調査の結果（安定して作れるか、量の代理になっていないか）を見て決めます（grift-match の `docs/research/grouping-feasibility-2026-10.md`、別のセッションで作業中。軸の候補は §3.7）。
2. エンジニア側の希望（actor brief）を入れるか。入れるなら、項目は「やりたい場所・避けたい場所、あってほしい確かめ方、共有できる記録、本人のひとこと」の 4 群でよいか。進め方の希望は最初の版で外してよいか。
3. 0.9.0 に入れる範囲。推奨は段階 1（§1.4 の修正、文と問い、strength と relationship を Markdown から外す）です。`--top` の改名（在庫 #9）を同じ版に入れるかも決めてください。
4. 本人向けの文を出す相手を、本人申告と同意の記録があるとき（claimed）に限ってよいか。SES 企業が管理者として登録した identity（verified）には出さない案です。
5. strength（weak / moderate / strong）を JSON から消す時期。推奨は 0.9.0 では Markdown から外すだけにし、JSON は actor brief と同じ次の schema 版で消すことです。
