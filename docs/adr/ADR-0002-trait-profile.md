# ADR-0002: 特性は本人の仕事の割合と形を平易な文で書き、タイプ名を付けずに両側から照らす

- ステータス: 採択（2026-10-26、段階 1 の範囲。ラベルは付けない）
- 日付: 2026-10-26
- 関連: [設計書](../design/trait-profile-20261026.md)、[ADR-0001](ADR-0001-v08-no-volume-ordering.md)、[ギャップ表](../GAP-site-vs-cli-v08-20261025.md) 行 8・9・10、[0.8.x 計画](../PLAN-v080-20261025.md) 在庫 #6〜#9、[利用規範](../norms.md) §1・§2・§4・§5・§7

## 文脈

ユーザーの目的は、MBTI 診断のように順位づけはしないが、その人の特性に合わせて案件と照らせるようにすることである。使い手は SES の営業（非エンジニア）、案件側の担当者、エンジニア本人の 3 者である。

0.8.0 の出力は、数字と分母は正しく出している。それでも合成リポジトリ 4 本で `grift actor` / `grift project` / `grift align` を実行した Markdown を 3 者の目で読むと、33 か所で詰まる（設計書 §1.3。内部名 11、数字だけ 8、順位・良し悪し 7、食い違い 7）。

| 場所 | 実体 | 読み手に起きること |
|---|---|---|
| actor の Markdown | 言葉による最初の説明（「## 傾向」）が 139 行中の 96 行目 | 営業が、進め方を自分の言葉で説明できない |
| `tendency.py:103-110` | 間隔の中央値が取れれば `regular_submission_direction`、強さは常に `moderate` | 数日おきに出す人にも、まとめて出して 30 日以上空く人にも「定期的な変更提出の傾向」と出る |
| `tendency.py:49-54` | `strength: weak / moderate / strong` | 2 人を並べると、片方が「強い人」に読める |
| `tendency.py:200-217` | `relationship` が 1 人の件数とチーム全体の件数の比で向きを決める | 両方とも backend が最も多いのに `different_direction` と出る |
| align の Markdown | 軸ごとの並び（5 通り）だけを出す | 面談で何を聞けばよいかが出ない（ギャップ表 行 8） |
| align の入口 | 案件の宣言 → 本人の観測の向きだけ | エンジニア側が案件に求めることを書けない（ギャップ表 行 9） |

MBTI の分かりやすさの中心はタイプ名である。しかし型に畳むと分母が消える（ギャップ表 行 10、架空の物語「スコアにした途端、条件が見えなくなる」）。The Myers & Briggs Foundation が公開している MBTI の倫理規定も、結果を人のラベル付け・評価・制限に使わないこと、採用の選別に使わないことを定めている（設計書 §2.1）。

## 決定

特性の出力に、次の 8 つの受入条件を課す。T1〜T7 は段階 1 から、T8 は段階 2 から適用する。

### T1. 文は量ではなく、本人の仕事の割合と形で選ぶ

文を選ぶのに、件数・日数・行数の大きさを使わない。使うのは「自分の変更のうち何件か」という割合と、間隔の形（真ん中の値と、10 回に 9 回が収まる値）だけとする。量の数字は根拠として残す。

### T2. 比べる相手は本人のほかの仕事だけ

「多い」は本人の変更の中で多いという意味で使う。ほかの人、ほかのリポジトリ、参照分布と比べた語（上位、平均より）を文に入れない。

### T3. 文ごとに分子・分母・期間を置く

文の数字は同じ段落か根拠の表に、分子・分母・期間と一緒に置く。母数が 20 に届かない割合は出さない（`MIN_POPULATION_FOR_RATES` と同じ）。

### T4. タイプ名を作らない

軸ごとの文を 1 つの名前や語の組み合わせに畳まない。JSON に、文、文の id、型を表すキーを置かない。文は Markdown にだけ出し、決定表で JSON の数字から作り直せるようにする。

### T5. 照らし合わせを合計しない

「重なった項目の数」「N 項目中 M 項目」を出さない。重なっている点は表に、確かめたい点は問いとして並べる。

### T6. 文と問いは公開した決定表で選ぶ

文と問いは、設計書 §3.2 と §3.4 の決定表で数字から機械的に選ぶ。LLM は使わない。決定表は docs と定数の 2 か所に置き、片方だけ変えると両方の値を挙げて落ちるテストで結ぶ。決定表を変えるときは `DEFINITION_VERSION` を上げる。

### T7. 本人向けの文は、本人申告と同意の記録があるときだけ出す

`attribution_state=claimed` かつ `consent=recorded-explicit-consent` のときだけ、特性の文を出す。公開リポジトリの第三者（`inferred_actor`）、管理者が登録した identity（`verified`）、collection（`--all` / `--top`）には出さず、`not_observed` とする。norms §4 が本人向けの表示を claimed にだけ許していることに合わせる。

### T8. エンジニア側の宣言は希望として受け、観測と混ぜない（段階 2）

`tep-actor-brief-v1` は、エンジニアが案件に求めること（やりたい場所・避けたい場所、あってほしい確かめ方、共有できる記録）と、本人のひとことを受ける。できることの申告は受けない。希望と案件のリポジトリの観測は ADR-0001 R5 と同じ 5 通りで並べ、宣言どうし（共有できる記録と、案件が求める記録）は別の欄に置く。本人のひとことは確かめず、申告と明記してそのまま載せる。

## 採択した範囲と決定（2026-10-26）

ユーザーは 2026-10-26 に、設計書 §8 の 5 つの判断に結論を出した（親セッション経由）。ラベルの判断（§8 の 1）は同じ日にグルーピング調査の判定を受けて決めた。

| 範囲 | 中身 |
|---|---|
| 採択 | T1〜T7 を段階 1（0.9.0）の受入条件とする。T4 は「群やタイプ名を出さない」として適用する |
| 採択 | 本人向けの文は claimed と同意の記録があるときだけ出す（T7）。verified には出さず、出していない理由を書く |
| 採択 | strength は 0.9.0 では Markdown から外すだけにし、JSON の `strength` は非推奨と書いて残す。消すのは次の schema 版 |
| 採択 | actor brief（T8）は段階 2 で入れる。0.9.0 には入れない |
| 採択 | `--top` の改名は 0.9.0 に入れない |
| 決定 | ラベル（群やタイプ名）は付けない（2026-10-26、[grift-match#4](https://github.com/Cor-Incorporated/grift-match/pull/4) の判定 C を受けて）。エンジニア側の群は人の進め方ではなく「どの repo（言語・流儀）の人か」の言い換えだった（群の情報の 60% が repo で説明される。U = 0.601）。repo の平均を引くと、どの群の数でもシルエットは 0.15〜0.18 で、型の切れ目は無かった。案件側は標本が 19 本で下限の 20 本に届かず、判定不能だった。T4 は「群やタイプ名を出さない」のまま確定する。報告: [`docs/research/grouping-feasibility-2026-10.md`](https://github.com/Cor-Incorporated/grift-match/blob/cf0d148/docs/research/grouping-feasibility-2026-10.md) |

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 軸ごとの語の組み合わせ（設計書の案 B。例「サーバー側中心・間を空けずに・単体テストあり」） | 組み合わせがタイプ名と同じ働きをし、語だけが転記されると件数と期間が消える。語の境目を越える操作の得が大きく、表計算で語を絞り込めば境目による選別になる |
| 16 タイプのような型 | 同上。二択の境目の近くの人を反対側に振り分ける。MBTI の倫理規定も選別に使わないと定めている |
| 参照分布の位置を文にする（例「公開リポジトリの上位 3 割」） | ADR-0001 R3。人の順位に読まれる |
| LLM で文を作る | 同じ入力で同じ文にならず、検算できない |
| 件数どうしの比で向きを出す（0.8.0 の `relationship`） | 1 人とチームの件数は同じ物差しではない。割合どうしで比べるか、件数の軸では出さない |

## 未対処として記録するもの

- `strength` を JSON から消すのは、次の schema 版（段階 2）とした（2026-10-26）。0.9.0 では Markdown から外すだけで、JSON のキーは非推奨として残る
- actor brief に進め方（間隔）の希望を入れるか。案件のリポジトリの間隔はチームの出し方で、1 人の働き方の条件と同じ物差しになるかが分からない（未検証）
- `verify` は Markdown を見ない。受け取った人が JSON を検算して Markdown を作り直せる仕組み（たとえば `grift render`）は、この ADR では決めない
- surface の傾向が未観測の割合を 0.0 として並べる疑い（設計書 §1.4 の 9、未再現）
- `relationship` の修正が外部の道具（grift-sales-poc など）に与える影響（未検証）
