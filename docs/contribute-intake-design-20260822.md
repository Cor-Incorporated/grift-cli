# チャネル3 受け口設計案 — `grift contribute` 提出物の受領（2026-08-22）

**対象**: grift-cli-dev（docs のみ。CLI / 受け口の実装はしない）
**正本**: BD `tep-data-collection-ruling-20260822.md` §2–3
**CLI 側**: `grift contribute` は v0.5.2 サイクルで実装予定。本ファイルは提出物を**受ける側**の設計。
**裁定（追記15）**: 提出用公開リポへの PR を正、フォーム不採用、メールは副。**条件1点（必須）**: contribute の確認フローに「この提出は公開リポジトリに載る」を明示する。PR 方式は payload が公開になる。

## 0. 動かさない境界

- CLI からの自動送信は恒久禁止（同裁定 §1）。受け口は「本人が選んで送る」だけを扱う。
- payload 規則（上書き禁止）: repo-scope の集計値・context_profile・定義版のみ。
  **canonical_id・actors・メール・パス・repo 名（本人が付記を選ばない限り）・tenant スコープ値は含めない。**
- 用途拘束: TEP Report 集計と参照分布 vNext 以外に使わない。
- 分布算入は既存規則のまま（MIN_N=30・immutable 版管理・リーグテーブル禁止）。

## (a) 提出経路の比較と推奨

| 経路 | 利点 | 欠点 | 個人情報 | 機械検証 | 人間可視のレビュー点 |
|---|---|---|---|---|---|
| GitHub 提出用公開リポへの PR | 履歴が残り、CI で reject できる。撤回は削除 PR。既存の docs-only PR 文化と一致 | GitHub アカウントが要る。merge 前でも fork/branch にファイルが残る | validator が default へ載せない限り、PII は default に乗らない | Actions で schema + 禁止語を red | ある（PR） |
| フォーム（第三者ホスト） | 摩擦が低い | 処理者が第三者。監査境界の外。撤回と保持の契約が薄い | 回答メタ（メール等）が残りやすい | 後段バッチになり、reject が遅れる | 弱い |
| メール添付 | アカウント不要 | ヘッダに個人が付く。CI が無い。inbox 保持が別問題 | 経路自体が個人情報を運ぶ | 人手で同じ validator を後追い | 弱い（inbox） |

**正経路（追記15で確定）: 提出用公開リポへの PR。**

理由:

1. 裁定 §2 は受け口を「最小」とし、3案を列挙して Report 設計時に決める、とだけ書いた。最小かつ既存運用（月次 KPI も直 push せず PR）に揃えるなら、提出も PR が一本で足りる。
2. validator を CI にして、禁止フィールド混入を **merge 前に自動 reject** できる。フォーム/メールは同じ検査を後段に回すことになり、一度 inbox/シートに載った個人情報を消す作業が残る。
3. 人間可視のレビュー点が残る。用途拘束（Report / vNext 以外に使わない）を PR 本文で毎回再掲できる。
4. メールはアクセシビリティ用の副経路に下げ、受領側がヘッダを捨てて同一 validator に通してから PR 化する（正経路のコピーであり、別ルールを増やさない）。

フォームは採用しない（追記15で確定）。第三者処理と保持契約が、norms に書く保持・撤回と二重管理になる。

**未決（提唱者）**: 提出リポを `grift-cli` public の配下に置くか、専用 public リポにするか。専用の方が「製品コードと提出物を混ぜない」「保持期間後の tombstone が製品履歴を汚さない」。

## (b) 受領時の機械検証（validator 案）

実装しない。v0.5.2 の `grift contribute` が書く payload と、受け口 CI が読む規則を同じ allowlist にする（doc-code パリティ）。

### 入力

単一 JSON（拡張子 `.json`）。ファイル名に repo 名・個人・メールを含めない（`contrib-YYYYMMDD-<short-random>.json` 等）。

### allowlist（受理してよいキー）

- `schema_version`（contribute payload 用の版。report-v1 をそのまま送らない）
- `analysis_scope` = `"repo"` のみ
- `definition_version` / `reference_version` / `tool_version`
- repo-scope の集計値（既存 report-v1 の集計フィールドに限定。actors / commits 明細は拒否）
- `context_profile`（PR-A の観測。個人識別子を持たないこと）
- 任意の付記フラグ: `repo_name_opt_in` が true のときだけ `repo_name` を許可

### 自動 reject（exit ≠ 0・PR を red）

裁定 §2 の禁止を機械にする。1件でも当たれば reject。**部分受理しない。**

| 検査 | 規則 |
|---|---|
| `canonical_id` | キー名または文字列値として出現したら reject |
| メール | `@` を含む文字列、`emails` / `email_patterns` キー |
| パス | 絶対パス、ホームディレクトリ、Windows ドライブレター、`.git/` を含む文字列 |
| tenant | `analysis_scope` が `repo` 以外、tenant 集計キー |
| actors / 明細 | `actors`・`commits`・生 author |
| repo 名 | `repo_name_opt_in` なしの `repo_name` / `html_url` / github リポ URL |
| 等級語 | 合否・順位・「優秀」等（norms 7条 / 語彙ゲートの既存方針） |

違反コーパス（受理してはいけない入力）を先に置き、validator 実装時は「違反を通したら red」をテストの本体にする（E10 / F-P10-3 の反証テスト規則）。

CLI 側（未実装）の確認フロー（追記15 条件・必須）:

1. 送信前に payload 全文を端末表示する
2. **同じ画面に次の文言を出す（省略不可・`--yes` でも消さない）**: 「この提出は公開リポジトリに載る」
3. `--yes` なしなら対話確認。確認に進む前に上記文言が見えていること
4. メール副経路でも、PR 化する前に提出者へ同じ文言を示す（経路で同意の中身を変えない）

受け口は「確認済み」を信じず、同じ規則で再検査する。PR 本文テンプレートにも同じ一文を再掲する。

## (c) 保持期間・撤回 — norms 追記用の条文案

条文番号は P1g の 1–7 条の続きを想定。番号は norms 正式化時に振り直してよい。

**第8条（提出の目的拘束）案**
opt-in 提出の用途は TEP Report の集計と参照分布の新版作成に限る。他目的（個別評価・営業リスト・再識別）への転用は非準拠。

**第9条（保持期間）案**
受領した payload は、(1) 発行済みの参照分布バージョンに算入された時点、または (2) 受領から 18 か月、の早い方まで保持し、その後 default 枝から取り除く（tombstone）。発行済み分布そのものは改変しない（第10条）。

**第10条（撤回）案**
提出者は、算入前であれば撤回できる。受け側はキューから除き、未発行の vNext に入れない。すでに immutable な分布バージョンとして発行したものからは、個別 payload を取り除けない。この限界を提出前に示す。git 履歴に残ったファイルの暗号学的消去は約束しない。約束できるのは default からの除去と、以後の版への非算入である。

**第11条（事故混入）案**
canonical_id / メール / パスが混入した提出は受理しない。merge 後に見つかった場合は default から除き、その payload はどの版にも算入しない。

## (d) 分布 vNext への算入手順

既存規則を参照する。新しい閾値は作らない。

1. **scope**: repo スコープ同士のみ。tenant 値を repo 分布に載せない（`INSTRUCTION-v1-definition-b-20260822.md` §0 / WP2）。
2. **MIN_N**: 指標ごと n<30 は位置を出さない（`reference_too_small`）。opt-in が 30 未満なら、その指標は vNext に「位置なし」で残すか、版ごと見送りかを発行記録に書く。閾値 30 は下げない。
3. **immutable**: 現行ファイルを書き換えない。次版は別ファイル（例: v2026.09 を残し v2026.11 / 以降を新設）。レポートは使った版を記す。
4. **算入集合**: validator 通過かつ撤回されていない payload のみ。公開 corpus（チャネル2）と opt-in（チャネル3）を混ぜる場合は、版メタに内訳 n を書く。個別値のリーグテーブルは出さない。
5. **判別基準**: 5f2665e は凍結のまま。再走結果は新版 DISCRIMINANT に逐語。

```
受領 PR → CI validator →（人間レビュー）→ 算入キュー
    → 指標ごと n 集計 → MIN_N 判定 → 新版ファイル発行
    → 旧版は残置 → 算入済み payload は保持期間規則で tombstone
```

## 要約（追記15で経路は確定）

| 項目 | 決定 | 理由 |
|---|---|---|
| 正経路 | 提出用公開リポへの PR | 機械 reject と人間レビューを同じ場所に置ける |
| 副経路 | メール → 人手で validator → 同じリポへ PR | アカウント無しの受け皿。ルールは増やさない |
| フォーム | 採用しない | 第三者処理と保持が norms と二重になる |
| 確認フロー | 「この提出は公開リポジトリに載る」を明示 | PR 方式は payload が公開になる（追記15 条件） |
| 実装時期 | CLI は v0.5.2 サイクル。受け口 CI は CLI と同時 | 片方だけの出荷は「送れるが受け取れない」 |

実装票・スキーマ凍結・リポ新設は別指示。CLI 実装時は上記確認文言を落とさない。
