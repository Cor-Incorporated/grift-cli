## (2) 署名付きアテステーション（attest bundle）設計文書

### 目的

「受領者が対象リポジトリにアクセスできない場合でも、**誰が・どの条件で測ったか**を検証できる」ようにする。§9-1 のとおり、コードは MIT で模倣可能であるため、moat は「証拠の信頼チェーン」側に作る。

### bundle の中身（attest-v1）

```json
{
  "attest_schema": "tep-attest-v1",
  "subject": {
    "repo_hint": "owner/name または null（提出者の選択・null であれば非開示）",
    "commit_sha": "<40hex>",
    "report_sha256": "<report.json の sha256>"
  },
  "conditions": {
    "definition_version": "tep-vX.Y.Z-...",
    "origin_definition_version": "...",
    "activity_definition_version": "...",
    "context_definition_version": "...",
    "tool_version": "grift X.Y.Z",
    "analysis_scope": "repo",
    "reference_version": "v2026.11",
    "identity_digest": "<config_digest（identity.toml の sha256・既存実装を再利用）>"
  },
  "executed_by": {
    "signer_identity": "<署名鍵に紐づく識別子（sigstore では SAN/email、git 署名では key fingerprint）>",
    "executed_at": "<UTC>",
    "runner_hint": "local|ci:<runner>（過剰な環境情報は含めない）"
  },
  "verification": {
    "method": "grift verify --bundle bundle.json --repo <path|url>",
    "notes": "repo アクセスがあれば report_sha256 を再計算で突合。無ければ署名と subject の整合のみ検証（CANNOT_VERIFY-repo となり理由を明示）"
  }
}
```

**含めないもの**: report 本文（bundle は参照のみ・report は別ファイル）・メール・パス・tenant スコープ値・repo 名（repo_hint は提出者の opt-in）。

### 署名方式の比較（独自暗号実装は禁止）

| 方式 | 便乗するもの | 長所 | 短所 | 推奨 |
|---|---|---|---|---|
| **sigstore（cosign）** | OIDC アイデンティティ + 公開透明性ログ（Rekor） | 鍵管理が不要（GitHub OIDC で署名）・透明性ログで改ざん検出が第三者検証可能・エコシステム成熟 | Python バンドルとしては `sigstore-python` 依存（純stdlib原則を破る）— **CLI の依存には入れず、`grift attest --sign cosign` で外部 cosign バイナリを呼ぶ形にすれば回避可** | **第一推奨** |
| **git 署名（SSH / gpg / gitsign）** | 既存の git コミット署名チェーン | 追加ツール不要（git と ssh-keygen で成立）・開発者にとって既存鍵の再利用 | bundle は git オブジェクトではないため「git 署名」の直接適用は不自然 — detached signature（`git hash-object` + ssh sign）で擬似適用は可能だが証明モデルが弱い | サブ（`--sign ssh` として提供） |
| **単純 detached sig（openssl dgst）** | openssl | 最小構成 | 鍵の所在が不明瞭 → 「誰が」の証明にならない（§9-1 の目的を満たさない） | 却下 |

**推奨構成**: `grift attest --sign cosign`（主・sigstore）+ `--sign ssh`（副・git 署名鍵を再利用する detached signature）。独自の暗号実装は行わない（指示どおり）。

### norms との整合（bundle 仕様に明記する文言）

> 署名は「**正しさ**」ではなく「**実行の事実**」の証明である。署名済み bundle は「この主体がこの条件でこの SHA を測った」ことを示すだけで、測定対象の価値・能力・品質を意味しない。bundle を合否や順位付けに使う利用は TEP 非準拠（norms 2条）。

### 受領者の検証体験

```
grift verify --bundle evidence/attest.json --report evidence/report.json --repo ./clone
  → 3層の結果を1行ずつ:
    SIGNATURE: VERIFIED (sigstore: alice@example, 2026-08-25, Rekor inclusion confirmed)
    REPORT HASH: MATCH (bundle.subject.report_sha256 == 実 report.json sha256)
    RECOMPUTE: VERIFIED | MISMATCH | CANNOT_VERIFY(repo inaccessible)
```

repo が無ければ SIGNATURE + REPORT HASH のみ（RECOMPUTE は理由つきでスキップ）— 「リポジトリ非アクセスでも誰がどの条件で測ったかの検証」がこの 2 層で成立する。

### 反証テスト設計

1. **改ざん束の検出**: report.json の 1 フィールドを書き換え → `REPORT HASH: MISMATCH`
2. **bundle 改ざん**: subject.commit_sha を変更して再署名なし → `SIGNATURE: INVALID`
3. **条件差し替え**: conditions.definition_version を書き換え → 署名対象ダイジェストが変わるため `SIGNATURE: INVALID`
4. **repo 不在**: `--repo` なし → `RECOMPUTE: CANNOT_VERIFY (repo not provided)` で他 2 層は VERIFIED
5. **未署名 bundle** → `SIGNATURE: UNSIGNED`（警告つき・検証は続行しない設計）

### 0.6 に含めるか 0.7 か — 推奨と根拠

**0.6.0 に含める（P0）**。根拠: (a) 外部評価 §9 が moat の第 1 位に位置づけ、告れい（プロモーション）前に「証拠の信頼チェーン」が体験できる状態が望ましい (b) 実装の中心は**参照とダイジェストの束**であり暗号は既存エコシステム（cosign/ssh-keygen 呼び出し）に丸投げするため、純stdlib原則を守ったまま数週間の規模 (c) verify との統合（既存 3 値に層を足す）は v0.6 の PR-B/C と同じ API サーフェスで提供でき、後付けより一貫する。リスク（cosign バイナリの普及度）は `--sign ssh` のサブ経路で緩和する。

## (4) スコープ外の明文化（非目標）

**v0.6 でも実装しない**:

- **意味的品質評価**（設計・可読性・保守性・複雑性の AI/AST 解析）— Gitty の領域であり、評価ではなく証拠化という軸を守る
- **ランキング・人材検索・スカウト** — LAPRAS/Findy の領域。TEP は判定機ではない
- **年収推定・市場価値スコア** — 報酬データを持ちません
- **予測妥当性の主張**（採用後活躍・納期遵守・障害率との相関）— 実証されておらず、今後も「分離できた/できなかった」の記述に留める
- **複合スコア・等級語彙・重み付け** — 7つの禁止の中核。競合評価 §6 の「値を能力の代理変数にしない」を恒久遵守

これらは競合評価の最終判定「採用スコア競争へ戻らないことが条件」との整合である。
