# verify が保証すること、しないこと

[English](en/verify-guarantees.md)

`grift verify` は、保存した report が「渡された repo と入力から、同じ手順でもう一度作ると一致するか」を確かめます。ここでは、その保証の範囲を、偽装の手口（攻撃木）の形で書きます。報告書に載せた数字を受け取る人が、どこまで信じてよいかを決める材料にしてください。

## 先に結論

- verify が保証するのは、**report と repo の一貫性**です。report の JSON が、渡された git の履歴から再計算した結果と同じだと確かめます。
- verify が保証しないのは、**その repo の履歴が本物かどうか**です。commit の作者名・メール・日付は書いた人が決めた値で、git の仕組みだけでは本物だと言えません。
- 本物らしさを支える材料は、verify とは別にあります。公開 forge の記録、署名ヘッダの有無、attest による署名です。どれも偽装を不可能にはせず、偽装の手間を増やします。

## 攻撃木

目標は「実際より良く見える report を、検算を通る形で作ること」です。

| 手口 | verify で防げるか | 防げる理由 / 防げない理由 | 手間を増やす材料 |
|---|---|---|---|
| 1. report の JSON の数字を書き換える | 防げる | 再計算の結果と食い違い、`MISMATCH` になります。signature_observation・usage_terms を書き換えても同じです | なし（verify で足ります） |
| 2. 別の repo や別の期間で作った report を、元の repo のものとして渡す | 防げる | 分析 SHA、観測日、入力のハッシュを provenance に残しており、渡された repo から再計算すると一致しません | なし |
| 3. `--as-of`・`--role-lens`・`--disclosure-level` などの条件を変えて作り直す | 防げる | 条件は provenance に記録され、verify はその条件で再計算します。条件を書き換えた report は一致しません | なし |
| 4. 定義版の違う report を照合する | 確かめられない | `CANNOT_VERIFY`（終了コード 2）になります。偽装ではなく、手順が違うためです | 該当する版の CLI で照合します |
| 5. 偽の履歴を持つ repo を作り、その repo で report を作る | 防げない | 再計算は、その偽の履歴に対しては一致します。verify が見るのは report と repo の一貫性だけです | 公開 forge の記録（次の行）、署名ヘッダ、attest |
| 6. commit の作者名・メール・日付を書き換えた履歴を作る | 防げない | 作者情報は自己申告です。identity ファイルも、ある人がそのメールを名乗るという宣言で、本人性の証明ではありません | forge の記録との突き合わせ、署名ヘッダ |
| 7. forge の記録（レビュー・課題）を手で作る | 一部だけ防げる | ローカルの export は作り手が書けます。`--fetch-public` で公開 API から取った記録は、公開側の記録として誰でも取り直せます。それでも API の応答が改ざんされていないことまでは、この CLI だけでは示せません | `--fetch-public` で取り、`--public-evidence` で同じ記録を再照合する |
| 8. 署名のない commit を、署名があるように見せる | 防げる（有無のみ） | 署名ヘッダ（`gpgsig`）の有無は commit オブジェクトから決まり、再計算できます。署名が正しいかどうかは、読む人の鍵に依存するため verify では見ません | `git verify-commit` を読む人が自分の許可した署名者で実行する |
| 9. 本物の署名者のふりをして report に署名する | 防げない（attest の範囲） | `grift attest` は report のハッシュに署名します。署名者が誰かは、受け取る人が信頼する鍵で決めます | `--allowed-signers` と `--principal` を受け取る側で固定する |
| 10. 作ったあとの日付を、もっと前だったように見せる | 防げない | 観測日は `--as-of` で選べる値で、時刻の証明ではありません | 第三者の時刻証明（現行版には無い。下の「まだ無いもの」） |

## 署名ヘッダの観測（0.9.6）

report-v2 には `signature_observation` があります。選んだ commit のうち、署名ヘッダを持つものの比率を、件数と母数つきで出します。母数が 20 に届かないときは `not_observed`（`insufficient_population`）です。

- 数えるのは**ヘッダの有無だけ**です。署名が正しいか、誰の鍵かは見ません。`%G?` の結果は、読む人の鍵束によって変わり、`grift verify` が再生できないためです。
- 署名がない commit は、正当な履歴にも普通にあります。この数は点数でも順位でもなく、足切りの材料にもなりません（[利用規範](norms.md)）。
- 署名の有効性を確かめたい人は、自分の許可した署名者で `git verify-commit` を実行してください。

## 手間を増やす、という言い方について

上の表の「材料」は、偽装を不可能にするものではありません。偽装に必要な手間（公開 forge に実在の記録を作る、署名鍵を用意する、複数の入力で矛盾なく作る）を増やし、受け取る人が突き合わせる場所を増やすものです。「改ざんできない」とは書きません。

## まだ無いもの

次は現行版にありません。必要なら受け取る側の運用で補ってください。

- 時刻の第三者証明（透明性ログへの記録など）。report のハッシュを外部に記録する運用は、利用者側で行えます。
- 署名者の身元の確認。attest は署名と report の対応を確かめますが、その鍵の持ち主が誰かは、受け取る人が決めます。
